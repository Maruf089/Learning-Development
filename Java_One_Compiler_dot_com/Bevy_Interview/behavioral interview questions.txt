1) Tell me about a time you led a technical task end-to-end.

Answer
Task: We needed a reliable way to sync data and updates across modules
Action: I took ownership of designing and implementing the sync method.
I introduced RabbitMQ messaging between modules, implemented Dead Letter Queue (DLQ) for rejected messages.
 I set up the necessary queues, exchanges, and bindings, and ensured that messages were processed idempotently to avoid duplicate updates. 
I improved reliability and observability of sync failures, reduced manual debugging time.


2) Describe a time you disagreed with another engineer/PM/manager. What did you do?

They wanted to use a simpler resttemplate-based sync approach without messaging.
I explained the tradeoffs: simpler initial implementation vs long-term reliability and scalability.
I proposed a proof-of-concept RabbitMQ implementation to demonstrate its benefits.
After evaluating both approaches, the team agreed that messaging was the better long-term solution.

3) Tell me about a time you made a mistake in production. How did you handle it?
Answer
Mongo aggregation query caused high CPU load in production.
Because of this data sync failed in production database.
I need to solve this quickly.
I restore the database from backup to reduce impact.
Then I analyzed the query using explain plan, identified inefficiencies, and optimized the aggregation pipeline.
I deployed the optimized query after testing it in staging, which resolved the CPU load issue.
I documented the incident and shared learnings with the team to prevent similar issues in the future.

4) Give an example of when you improved system performance?
Answer
Import exel file api was slow when importing large files.
I profiled the API to identify bottlenecks and found that processing was done sequentially. 
I refactored the import logic to use parallel processing allowing multiple rows to be processed concurrently.
This change reduced the import time by 70% for large files.

5) Give an example of when you improved system scalability?
Answer
One single database was handling all read and write operations causing performance bottlenecks as user base grew.
I implemented database replication to separate read and write operations.
Read replicas handled read-heavy operations, while the primary database focused on writes.
This change improved overall system scalability and reduced latency for read operations.
