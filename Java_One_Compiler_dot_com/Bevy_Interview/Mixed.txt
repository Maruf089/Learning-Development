Stream API in Java provides a functional approach to process sequences of elements (like collections) in a declarative way. It allows you to perform operations such as filtering, mapping, and reducing on data in a concise and readable manner.
Key features of Stream API include:
1. Laziness: Stream operations are lazy, meaning they are not executed until a terminal operation is invoked. This allows for efficient processing of large datasets.
2. Functional Programming: Stream API leverages functional programming concepts, allowing you to use lambda expressions and method references for defining operations.
3. Parallel Processing: Stream API supports parallel processing, enabling you to process data concurrently for improved performance on multi-core processors.

Example:  
List<String> names = Arrays.asList("Alice", "Bob", "Charlie", "David");
List<String> filteredNames = names.stream()
    .filter(name -> name.startsWith("A"))
    .collect(Collectors.toList());
In this example, we create a stream from a list of names, filter the names that start with "A", and collect the results into a new list.

Stream is not resuable; once a terminal operation is performed, the stream is considered consumed and cannot be used again. To perform multiple operations, you need to create a new stream from the source data each time.

What is the difference between Checked and Unchecked Exceptions in Java?

Checked Exceptions: 
Checked exceptions are exceptions that are checked at compile-time. This means that the compiler requires you to handle these exceptions either by using a try-catch block or by declaring them in the method signature using the throws keyword. Examples of checked exceptions include IOException, SQLException, and ClassNotFoundException.
Unchecked Exceptions:
Unchecked exceptions, also known as runtime exceptions, are not checked at compile-time. These exceptions can occur during the execution of the program and do not require explicit handling. Examples of unchecked exceptions include NullPointerException, ArrayIndexOutOfBoundsException, and IllegalArgumentException.

What is the difference between an Abstract Class and an Interface in Java?

Abstract Class:
An abstract class is a class that cannot be instantiated on its own and may contain both abstract methods (without implementation) and concrete methods (with implementation). Abstract classes are used to provide a common base for subclasses and can have member variables, constructors, and access modifiers. A class can extend only one abstract class (single inheritance).
Interface:
An interface is a contract that defines a set of abstract methods that implementing classes must provide. Interfaces can only contain method signatures (until Java 8, after which default and static methods were introduced) and constants. Interfaces are used to achieve multiple inheritance in Java, as a class can implement multiple interfaces. Interfaces do not have constructors or member variables (except for constants).

Example:
// Abstract Class 
abstract class Animal {
    abstract void makeSound();
    
    void eat() {
        System.out.println("This animal eats food.");
    }
}
// Interface
interface Flyable {
    void fly();
}
class Dog extends Animal {
    void makeSound() {
        System.out.println("Woof Woof");
    }
}
class Bird extends Animal implements Flyable {
    void makeSound() {
        System.out.println("Chirp Chirp");
    }
    
    public void fly() {
        System.out.println("This bird can fly.");
    }
}

Multiple Inheritance is not supported in Java through classes to avoid complexity and ambiguity that arises from the "Diamond Problem," where a class could inherit conflicting implementations from multiple parent classes. Instead, Java supports multiple inheritance through interfaces, allowing a class to implement multiple interfaces without the issues associated with class-based multiple inheritance.
Example:
interface A {
    void methodA();
}
interface B {
    void methodB();
}
class C implements A, B {
    public void methodA() {
        System.out.println("Method A implementation");
    }
    
    public void methodB() {
        System.out.println("Method B implementation");
    }
}

What is Diamond Problem in Java?
The Diamond Problem is a scenario in object-oriented programming where a class inherits from two classes that both inherit from a common superclass. This creates ambiguity when the subclass tries to access methods or properties defined in the common superclass, as it is unclear which path to follow.

Example of Diamond Problem (not allowed in Java):
class A {
    void display() {
        System.out.println("Class A");
    }
}
class B extends A {
    void display() {
        System.out.println("Class B");
    }
}
class C extends A {
    void display() {
        System.out.println("Class C");
    }
} 
class D extends B, C { // This will cause a compilation error
    void show() {
        display(); // Ambiguity: Which display() method to call?
    }
} 
How C++ solves Diamond Problem:
C++ solves the Diamond Problem using virtual inheritance. When a class is declared as a virtual base class, it ensures that only one instance of the base class is created, regardless of how many times it is inherited in the hierarchy. This eliminates ambiguity and ensures that there is a single path to access the members of the common base class.
class A { 
    void display() {
        std::cout << "Class A" << std::endl;
    }
};
class B : virtual public A {
    void display() {
        std::cout << "Class B" << std::endl;
    }
};
class C : virtual public A {
    void display() {
        std::cout << "Class C" << std::endl;
    }
};
class D : public B, public C {
    void show() {
        display(); // No ambiguity: Calls A's display() method
    }
};

Thread pool in java :
A thread pool in Java is a collection of pre-instantiated threads that are ready to execute tasks. Instead of creating a new thread for each task, which can be resource-intensive and time-consuming, a thread pool allows you to reuse existing threads to handle multiple tasks. This improves performance and resource management in concurrent applications.
Java provides the Executor framework, which includes classes like ThreadPoolExecutor and Executors, to create and manage thread pools easily.
Example:    
ExecutorService executorService = Executors.newFixedThreadPool(10); // Create a thread pool with 10 threads
for (int i = 0; i < 20; i++) {
    final int taskId = i;
    executorService.submit(() -> {
        System.out.println("Executing task " + taskId + " by " + Thread.currentThread().getName());
    });
}   
executorService.shutdown(); // Shutdown the executor service after task completion

What is the difference between Synchronous and Asynchronous programming?
Synchronous programming is a programming paradigm where tasks are executed sequentially, one after the other. Each task must complete before the next task begins, leading to potential blocking and delays if a task takes a long time to finish.
Asynchronous programming, on the other hand, allows tasks to be executed independently. Tasks can start and complete at different times, enabling non-blocking operations.

Thread lifecycle in Java:
1. New: A thread is created but not yet started.
2. Runnable: The thread is ready to run and is waiting for CPU time.
3. Running: The thread is currently executing.
4. Blocked/Waiting: The thread is waiting for a resource or event.
5. Timed Waiting: The thread is waiting for a specified period.
6. Terminated: The thread has completed its execution or has been stopped.
7. Dead: The thread is no longer alive and cannot be restarted.
Example:

    System.out.println("Thread is running.");
});
thread.start(); // Moves thread to Runnable state

What is the difference between Future and CompletableFuture in Java?
Future is an interface that represents the result of an asynchronous computation. It provides methods to check if the computation is complete, to wait for its completion, and to retrieve the result. However, Future does not support chaining or combining multiple asynchronous tasks.
CompletableFuture is a class that implements the Future interface and provides additional features for handling asynchronous computations. It supports chaining, combining, and composing multiple asynchronous tasks using methods like thenApply, thenCompose. CompletableFuture also allows for better error handling and provides a more flexible way to work with asynchronous programming in Java.
Example:

executor.shutdown();

        Thread.sleep(1000);
    } catch (InterruptedException e) {
        e.printStackTrace();
    }
    return 42;
});
completableFuture.thenAccept(result -> {
    System.out.println("Result: " + result);
});

You should not mutate a element present in hash-based collection (like HashMap, HashSet) because it can lead to inconsistent behavior and make the collection unreliable. 
When you mutate an element that is used as a key in a hash-based collection, it can change the hash code of the object, which affects its position in the collection. This can result in the inability to retrieve the object later, as the collection may not be able to locate it using the original hash code.For example, if you have a HashMap with a mutable key object and you change the state of that key object after it has been added to the map, the hash code of the key may change. As a result, when you try to retrieve the value associated with that key, the map may not be able to find it because it is looking for the key using its original hash code, which no longer matches the mutated key's hash code.To avoid such issues, it is recommended to use immutable objects as keys in hash-based collections. Immutable objects have a fixed state that cannot be changed after they are created, ensuring that their hash code remains consistent throughout their lifecycle.
Example of mutable key issue:

    private String key;

    public MutableKey(String key) {
        this.key = key;
    }

    public void setKey(String key) {
        this.key = key;
    }

    @Override
    public int hashCode() {
        return key.hashCode();
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (!(obj instanceof MutableKey)) return false;
        MutableKey other = (MutableKey) obj;
        return key.equals(other.key);
    }
}

Function Composition in Java:
Function composition in Java refers to the process of combining two or more functions to create a new function. This is typically done using the Function interface from the java.util.function package, which provides methods like andThen() and compose() to facilitate function composition.
Example:  
Function<Integer, Integer> add2 = x -> x + 2;
Function<Integer, Integer> multiply3 = x -> x * 3;  
Function<Integer, Integer> addThenMultiply = add2.andThen(multiply3);
int result = addThenMultiply.apply(5); // (5 + 2) * 3 = 21  
Function<Integer, Integer> multiplyThenAdd = add2.compose(multiply3);
int result2 = multiplyThenAdd.apply(5); // (5 * 3) + 2 = 17

What is the difference between map() and flatMap() in Java Streams?
map() is used to transform each element of a stream into another form by applying a function to each element. The result is a stream of the transformed elements.
flatMap() is used to transform each element of a stream into a stream of other elements, and then flattens those streams into a single stream. It is typically used when the transformation function returns a stream or a collection.
Example:
List<String> words = Arrays.asList("Hello", "World");
// Using map() to convert each word to uppercase  
List<String> upperCaseWords = words.stream()
    .map(String::toUpperCase)
    .collect(Collectors.toList());

// Using flatMap() to split each word into characters and flatten the result
List<String> characters = words.stream()
    .flatMap(word -> Arrays.stream(word.split("")))
    .collect(Collectors.toList());


Higher Order Functions in Java:
Higher-order functions are functions that can take other functions as arguments or return functions as their result. In Java, higher-order functions can be implemented using functional interfaces and lambda expressions.
Example:  
// A higher-order function that takes a Function as an argument
public static <T, R> List<R> transformList(List<T> list, Function<T, R> transformer) {
    return list.stream()
               .map(transformer)
               .collect(Collectors.toList());
} 
// Usage:
List<Integer> numbers = Arrays.asList(1, 2, 3, 4, 5);
List<Integer> squaredNumbers = transformList(numbers, n -> n * n); // [1, 4, 9, 16, 25]

4 pre defined functional interfaces in Java are:
1. Function<T, R>: Represents a function that takes an argument of type T and returns a result of type R.
2. Predicate<T>: Represents a boolean-valued function that takes an argument of type T and returns true or false.
3. Consumer<T>: Represents a Consumer that takes an argument of type T and returns no result.
4. Supplier<T>: Represents a supplier of results, providing a method that returns a result of type T without taking any arguments.

What is Distributed Tracing?
Distributed tracing is a method used to track and monitor requests as they propagate through various services in a distributed system or microservices architecture. It provides visibility into the flow of requests, helping to identify performance bottlenecks, latency issues, and errors across multiple services.
Distributed tracing typically involves assigning a unique trace identifier to each request, which is passed along as the request moves through different services.
Popular distributed tracing tools include Jaeger, Zipkin, and OpenTelemetry, which provide visualization and analysis of trace data to help developers understand the behavior of their distributed systems.

Key concepts of Distributed Tracing.
Distributed tracing consists of two main concepts
  Trace Id
  Span Id

Trace Id is used to trace an incoming request and track it across all the composing services to satisfy a request.
Span Id is more of spans in between service calls to track each request that is received and to the response that is sent out.

Cascading Problem in Microservices:
Cascading failure in microservices refers to a situation where the failure of one service leads to the failure of other dependent services, resulting in a chain reaction that can bring down the entire system. This can occur when services are tightly coupled or when there is a lack of proper error handling and resilience mechanisms in place.
To mitigate cascading failures, microservices architectures often implement patterns such as circuit breakers, retries, timeouts.


Retry Pattern in Microservices:
The retry pattern in microservices is a resilience strategy used to handle temporary failures when communicating between services. This helps improve the overall reliability of the system by allowing temporary errors to be resolved without immediate failure.

Why AOP is needed for retry pattern implementation?
AOP allows you to separate the retry logic from the business logic, making the code cleaner and easier to maintain. By using AOP, you can apply the retry behavior declaratively through annotations, without cluttering the core functionality of your services.


ELK Stack:
ELK Stack is a collection of three open-source products: Elasticsearch, Logstash, and Kibana. It is used for searching, analyzing, and visualizing log data in real-time.
Elasticsearch is a distributed search and analytics engine that stores and indexes log data.
Logstash is a data processing pipeline that ingests log data from various sources, transforms it, and sends it to Elasticsearch.
Kibana is a data visualization tool that provides a user interface for exploring and visualizing log data stored in Elasticsearch.

Distributed Tracing vs ELK Stack:
Distributed Tracing and ELK Stack are both used for monitoring and analyzing applications, but they serve different purposes.
Distributed Tracing focuses on tracking the flow of requests across multiple services in a distributed system. It provides insights into the performance and latency of individual services, helping to identify bottlenecks and failures in the request path.
ELK Stack, on the other hand, is primarily used for log management and analysis. It collects, stores, and visualizes log data from various sources, allowing you to search and analyze logs for troubleshooting and monitoring purposes.

MDC (Mapped Diagnostic Context) in Logging:
MDC is a feature provided by logging frameworks like Log4j and SLF4J that allows you to add contextual information to log messages. It is essentially a thread-local storage mechanism that enables you to store key-value pairs that can be included in log entries.
